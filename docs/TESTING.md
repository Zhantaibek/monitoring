# План тестирования (этап 4)

Принцип: **боевой QUIK не останавливается, ресурсы сервера искусственно не нагружаются.**
Сбои имитируются тестовым процессом и временно сниженными порогами.
Порядок: сначала тестовый стенд или любая Windows-машина, затем короткий контролируемый прогон
на боевом сервере в нерабочее время.

## 0. Автоматические тесты (машина разработчика)

```powershell
npm test
```
Покрыто: подтверждение состояний и защита от «дребезга», эскалация WARNING → CRITICAL,
восстановление после рестарта без повторного уведомления, пороги с гистерезисом, разбор
`tasklist`, `sc` (английский и русский вывод), `netstat` (локализованный LISTENING), `wevtutil`,
окна обслуживания через полночь (Asia/Bishkek), формат уведомлений по ТЗ.

## 1. Read-only проверка конфигурации на сервере

```powershell
.\runtime\node.exe --disable-warning=ExperimentalWarning .\dist\index.js --once
```
Однократно выполняет все проверки и печатает результат. Telegram и база данных не используются.
Убедитесь, что все процессы, службы и порты QUIK в статусе `[OK]`.

## 2. Сценарии

Для тестов используйте отдельную копию `config.json` (переменная `CONFIG_PATH` в `.env`) или
временно правьте рабочий конфиг, а после тестов верните исходный.

| # | Сценарий | Действие | Ожидаемый результат |
|---|---|---|---|
| 1 | Остановка тестового процесса | В `processes` добавить `{ "label": "TEST dummy", "image": "quikmon-dummy.exe" }`. Выполнить `scripts\test-dummy-process.ps1 -Start`, дождаться стабильного состояния, затем `-Stop` | Через ~30 с одно сообщение `🔴 CRITICAL: QUIK PROCESS STOPPED`, повторов нет |
| 2 | Восстановление | `test-dummy-process.ps1 -Start` | Через ~30 с `🟢 RECOVERED` с длительностью сбоя; запись в `/history` |
| 3 | Перезапуск между проверками | `-Stop`, затем сразу `-Start` (быстрее 15 с) | `🟠 WARNING: QUIK PROCESS RESTARTED` со старым и новым PID |
| 4 | Порог CPU | Временно `thresholds.cpu = { "warning": 1, "critical": 99 }` | `🟠 WARNING: HIGH CPU USAGE` через ~90 с; после возврата порогов и рестарта — `RECOVERED` |
| 5 | Порог RAM | Аналогично: `thresholds.ram.warning = 1` | `🟠 WARNING: HIGH MEMORY USAGE` |
| 6 | Нехватка места на диске | Временно `thresholds.diskFree = { "warning": 99, "critical": 98 }` | `🔴 CRITICAL: LOW DISK SPACE` (диск не заполняется) |
| 7 | Потеря интернета | На стенде отключить сеть или указать в `.env` недоступный `TELEGRAM_PROXY_URL`. Во время «отключения» выполнить сценарий 1 | Сообщения копятся в очереди (`/status` покажет очередь). После восстановления связи приходят с пометкой «⏳ Доставлено с задержкой» и сообщение «СВЯЗЬ С TELEGRAM ВОССТАНОВЛЕНА» |
| 8 | Перезапуск бота | `Restart-Service QuikMonitor` | `⚪ МОНИТОРИНГ ОСТАНОВЛЕН`, затем `🔵 МОНИТОРИНГ ЗАПУЩЕН`. Уже известные проблемы не дублируются |
| 9 | Аварийное завершение бота | `Stop-Process -Id (Get-Content data\monitor.lock | ConvertFrom-Json).pid -Force` — только по PID из lock-файла, не по имени | Служба перезапускает процесс через 10 с; в стартовом сообщении «предыдущая работа завершилась аварийно» |
| 10 | Перезагрузка Windows | Плановая перезагрузка в окно обслуживания | После загрузки (отложенный старт ~2 мин) приходит `🔵 МОНИТОРИНГ ЗАПУЩЕН` с пометкой «сервер недавно перезагружен» |
| 11 | Без RDP-сессии | Выйти из RDP (Sign out, не Disconnect), выполнить сценарий 1 удалённо или дождаться события | Уведомления приходят, команды работают |
| 12 | Авторизация | Написать боту с другого аккаунта | Ответа нет, в логе `Отклонён запрос от неавторизованного пользователя` |
| 13 | Нагрузка самого бота | Диспетчер задач или `Get-Process node` в течение часа | CPU в среднем около 0%, кратковременные всплески во время проверок; память стабильна и не растёт (зафиксируйте базовое значение) |

После тестов: удалить тестовый процесс из `config.json`, вернуть пороги,
выполнить `Restart-Service QuikMonitor`, удалить `data\test\`.
