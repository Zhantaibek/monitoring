# Архитектура QUIK Server Monitor

## Принципы

1. **Только чтение.** Приложение не управляет QUIK, службами, сетью и firewall. Все внешние команды
   идут через одну функцию `src/utils/exec.ts`, где разрешены только `tasklist`, `sc query/queryex`,
   `netstat`, `wevtutil qe` из `System32`, без shell, с таймаутом.
2. **Минимум нагрузки.** Нет постоянного PowerShell/WMI. CPU, RAM, uptime и диски берутся из Node.js
   (`os.cpus`, `os.freemem`, `fs.statfs`) без запуска процессов. Один цикл всех проверок длится
   около 1,7 с (замер на Windows 11). Команды Telegram отвечают из кэша и проверок не запускают.
3. **Одна проблема — одно уведомление.** Состояние меняется только после N подряд одинаковых
   результатов (`confirm`). Для ресурсов есть гистерезис.
4. **Уведомления не теряются.** Каждое сообщение сначала пишется в SQLite (outbox), потом
   отправляется. При потере связи оно уходит позже с пометкой «доставлено с задержкой».
5. **Самовосстановление.** Служба Windows (WinSW) перезапускает процесс после сбоя. Состояние
   и инциденты переживают перезапуск и перезагрузку ОС.

## Механизмы мониторинга

| Проверка | Как | Интервал | Подтверждение |
|---|---|---|---|
| Процессы QUIK | `tasklist /FO CSV /NH`: число экземпляров ≥ `minInstances` | 15 с | 2 проверки (≈30 с) |
| Перезапуск между проверками | все PID процесса сменились | 15 с | сразу, разовое WARNING |
| Службы | `sc queryex <name>`: состояние `RUNNING` | 30 с | 2 проверки |
| Порты, `listen` | `netstat -ano`: порт в LISTEN, без подключения к QUIK | 30 с | 2 проверки |
| Порты, `connect` | TCP connect и сразу close (для внешних узлов) | 30 с | 2 проверки |
| CPU | разница `os.cpus()` между замерами, то есть среднее за 30 с | 30 с | 3 проверки (≈90 с) |
| RAM | `totalmem - freemem` (доступная физическая память) | 30 с | 3 проверки |
| Диски | `fs.statfs`, процент свободного места | 30 с | 3 проверки |
| Журнал System | `wevtutil qe` по `EventRecordID > последний` (Critical и Error) | 5 мин | разовая сводка |
| Сам монитор | ошибка выполнения проверки (`check:*`) | — | 3 ошибки подряд |

Метки состояний (`STATE`, `LISTENING`) в выводе утилит зависят от языка Windows. Поэтому разбор
опирается на значения, которые не локализуются: `4 RUNNING`, удалённый адрес `0.0.0.0:0`, коды выхода.
Это покрыто тестами.

### Пороги и гистерезис
`WARNING` выставляется при CPU > 85%, `CRITICAL` при CPU > 95%. Восстановление засчитывается
только когда значение опустится ниже порога минус `hysteresis` (5 п.п.). Для дисков действуют
пороги 15% и 5% свободного места и гистерезис 1 п.п. Всё настраивается в `config.json`.

### Окна обслуживания
Если у QUIK есть плановый ночной перезапуск, его время указывается в `maintenanceWindows`.
Переходы состояний внутри окна пишутся в историю, но уведомлений не создают. Если после окна
проблема осталась, приходит отдельное сообщение. Время окна задаётся в Asia/Bishkek; окно может
переходить через полночь.

### Журналы Windows
Читаются только метаданные: источник, код события, уровень и количество. Для Application Error
дополнительно берётся имя приложения. Текст событий не читается и в Telegram не уходит. При
первом запуске запоминается последний номер записи, поэтому старые события не присылаются.
После перезагрузки приходят события, накопившиеся за время простоя, например Kernel-Power 41
(неожиданное выключение).

## Хранение (SQLite, `data/monitor.db`)

| Таблица | Назначение |
|---|---|
| `incidents` | история инцидентов: начало, конец, максимальная серьёзность (`/history`) |
| `events` | журнал переходов и разовых событий, включая подавленные окном обслуживания |
| `check_state` | подтверждённые проблемы; после перезапуска повторного уведомления нет |
| `outbox` | очередь исходящих сообщений с повторными попытками |
| `kv` | служебные значения: последний `EventRecordID`, флаг корректной остановки |

Используется встроенный `node:sqlite` (Node ≥ 22.13), поэтому нативные модули и компиляторы не нужны.
Срок хранения задаёт `history.retentionDays` (180 дней).

## Безопасность

- Токен хранится только в `.env`. При установке права на файл получают Administrators, SYSTEM
  и учётная запись службы. Токен вырезается из всех логов, включая ошибки сетевых библиотек с URL.
- Бот отвечает только на `TELEGRAM_ADMIN_ID` и только в личном чате. Остальные запросы
  игнорируются и пишутся в лог (ID без текста сообщения).
- Накопившиеся команды при старте отбрасываются (`dropPendingUpdates`).
- Служба работает под `NT AUTHORITY\LocalService`, без прав администратора. Ей доступны
  `tasklist`, `sc query`, `netstat -ano` и чтение журнала System.
- Командные строки процессов, аргументы служб, тексты журналов, торговые данные и
  конфигурация QUIK не собираются.
- Входящие порты не открываются, правила firewall не меняются. Нужен только исходящий HTTPS
  до `api.telegram.org` (напрямую или через прокси).
- Node.js портативный и лежит в `runtime\`: в систему ничего не ставится, PATH не меняется.

## Внешний мониторинг (этап 8, архитектурный задел)

Бот на самом сервере не сообщит о потере питания, зависании ОС или обрыве сети. Схема на будущее:

```
  QUIK 172.23.10.82                                 Внешний сервер мониторинга
  ┌─────────────────┐   heartbeat (исходящий GET,    ┌─────────────────────────┐
  │ QuikMonitor     │ ──── каждые 60 с) ────────────►│ Uptime Kuma / аналог    │──► Telegram
  └─────────────────┘                                │  • push-монитор heartbeat│
           ▲                                         │  • ICMP ping 172.23.10.82│
           └──────────── ping / TCP-порт QUIK ───────│  • TCP-порт QUIK         │
                                                     └─────────────────────────┘
```

- В `.env` задаётся `HEARTBEAT_URL` (push URL), в `config.json` — `heartbeat.enabled: true`.
- Внешний монитор поднимает тревогу, если heartbeat не приходит N минут. Так ловятся и падение
  бота, и отключение сервера.
- Для ICMP и TCP-проверки снаружи на сервере ничего менять не нужно, кроме уже существующих
  сетевых правил.
- Файл `data/heartbeat.json` обновляется каждую минуту. Его могут читать локальные агенты (Zabbix и т.п.).
